# Inner Source 도입 로드맵

Inner Source는 오픈소스의 개발 방식(공개된 코드, 문서화된 기여 절차, 리뷰 기반 협업)을 **조직 내부**에 적용하는 것입니다. 이 문서는 dau_oss에서 연습한 OSS 운영 방식을 조직(학과 연구실, 동아리, 회사의 팀)에 옮기기 위한 단계별 계획입니다.

## 1. 왜 필요한가

| 현재의 문제 | Inner Source가 주는 변화 |
|-------------|--------------------------|
| 팀마다 같은 유틸리티를 따로 만듦 | 공용 저장소에서 찾아 쓰고, 부족하면 PR로 기여 |
| 다른 팀 코드의 버그를 발견해도 요청만 하고 기다림 | 직접 수정 PR을 보내 대기 시간 단축 |
| 지식이 특정 사람에게만 있음 | README, CONTRIBUTING, ADR로 문서화되어 남음 |
| 코드 품질 기준이 팀마다 다름 | 공통 리뷰 가이드와 CI로 기준 통일 |

## 2. 역할 정의

| 역할 | 책임 |
|------|------|
| Trusted Committer | 저장소의 리뷰·머지 권한 보유. 기여자를 멘토링하고 품질을 책임짐 |
| Contributor | 다른 팀 저장소에 이슈·PR로 기여 |
| Product Owner | 로드맵과 우선순위 결정, 외부 기여 수용 여부 판단 |
| Inner Source Champion | 도입을 이끌고 지표를 수집·공유 |

## 3. 단계별 로드맵

### 1단계 — 준비 (1~4주)

- [ ] 시범 저장소 1~2개 선정 (여러 팀이 함께 쓰는 공용 라이브러리가 적합)
- [ ] 조직 내 모든 구성원에게 읽기 권한 부여 (`internal` 가시성)
- [ ] 표준 문서 세트 작성: `README`, `CONTRIBUTING`, `CODE_OF_CONDUCT`, `CODEOWNERS`
- [ ] Trusted Committer 지정

**완료 기준**: 시범 저장소에 표준 문서 4종이 있고, 팀 밖의 사람이 문서만 보고 로컬 실행에 성공한다.

### 2단계 — 시범 운영 (2~3개월)

- [ ] PR 템플릿, 이슈 템플릿, 브랜치 보호 규칙 적용
- [ ] `[MUST]`/`[SHOULD]` 태그 기반 [리뷰 가이드](../REVIEW_GUIDE.md) 도입
- [ ] CI로 Lint/Test 자동 실행, 통과해야 머지 가능
- [ ] `good first issue` 라벨로 외부 팀이 시작하기 쉬운 이슈 표시
- [ ] 첫 외부 팀 기여 PR 3건 달성

**완료 기준**: 다른 팀에서 온 PR이 3건 이상 머지되고, 첫 리뷰까지 걸린 시간의 중앙값이 2 영업일 이내다.

### 3단계 — 확산 (3~6개월)

- [ ] 재사용 가능한 워크플로우와 저장소 템플릿을 조직 공용으로 배포
- [ ] 주요 기술 결정을 [ADR](../adr/README.md)로 기록하는 문화 정착
- [ ] Discussions의 RFC 절차로 팀 간 설계 논의 공개
- [ ] 저장소 검색 포털 또는 카탈로그 구축 (토픽 태그 표준화)
- [ ] 시범 사례를 사내 발표로 공유

**완료 기준**: Inner Source 저장소가 5개 이상이고, 각 저장소에 분기당 1건 이상의 외부 팀 기여가 있다.

### 4단계 — 정착 (6개월 이후)

- [ ] 기여 실적을 평가·보상 체계에 반영
- [ ] 지표 대시보드 자동화 (아래 지표를 주간 요약 워크플로우로 수집)
- [ ] 외부 공개가 가능한 프로젝트는 오픈소스로 전환 검토 ([라이선스 선택 기준](license-comparison.md) 적용)

## 4. 측정 지표

| 지표 | 정의 | 목표 |
|------|------|------|
| 외부 기여 비율 | 전체 머지 PR 중 소유 팀 밖에서 온 PR의 비율 | 10% 이상 |
| 첫 리뷰 응답 시간 | PR 생성부터 첫 리뷰까지의 중앙값 | 2 영업일 이내 |
| PR 리드타임 | PR 생성부터 머지까지의 중앙값 | 5 영업일 이내 |
| 재사용 저장소 수 | 2개 이상의 팀이 의존하는 저장소 수 | 분기마다 증가 |
| 문서 충족률 | 표준 문서 4종을 갖춘 저장소의 비율 | 90% 이상 |

dau_oss의 [DORA 보고서](../dora/report.md)와 PR Lead Time 워크플로우가 리드타임 지표 수집의 출발점이 됩니다.

## 5. 예상 위험과 대응

| 위험 | 대응 |
|------|------|
| 소유 팀의 리뷰 부담 증가 | Trusted Committer의 리뷰 시간을 업무로 인정, CODEOWNERS로 리뷰 분산 |
| 외부 PR이 방치됨 | SLA 추적 워크플로우로 응답 없는 PR·이슈를 자동 표시 |
| 보안상 공개하면 안 되는 코드 | 비밀 정보는 Secrets로 분리, 민감 저장소는 대상에서 제외 |
| "우리 코드"라는 소유 의식으로 인한 거부감 | 작은 성공 사례부터 공유, 관리자 층의 명시적 지지 확보 |
