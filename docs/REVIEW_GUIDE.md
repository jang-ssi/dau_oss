# 코드 리뷰 가이드

리뷰의 목적은 결함을 일찍 찾고, 코드에 대한 이해를 팀 전체로 넓히는 것입니다. 사람이 아니라 코드를 리뷰합니다.

## 1. 피드백 태그

모든 리뷰 코멘트는 아래 태그 중 하나로 시작합니다. 태그는 **작성자가 무엇을 해야 하는지**를 분명히 합니다.

| 태그 | 의미 | 작성자의 대응 |
|------|------|---------------|
| `[MUST]` | 머지 전에 반드시 고쳐야 함. 버그, 보안 문제, 규칙 위반 | 수정하거나, 근거를 들어 합의 |
| `[SHOULD]` | 고치기를 권장. 가독성, 유지보수성, 관례 | 수정하거나, 하지 않는 이유를 답글로 남김 |
| `[NIT]` | 사소한 취향. 오타, 이름 | 선택 |
| `[Q]` | 질문. 의도를 이해하기 위함 | 답변 |
| `[PRAISE]` | 잘한 점 | - |

### 코멘트 형식

```
[MUST] <한 줄 요약>

이유: <왜 문제인지>
제안: <어떻게 고치면 되는지, 가능하면 코드로>
```

예시:

> [MUST] `pull_request` 이벤트에서 Secret이 비어 있으면 배포 단계가 실패합니다.
>
> 이유: 포크에서 온 PR에는 Secrets가 전달되지 않습니다.
> 제안: `if: github.event_name == 'push'` 조건을 추가해 주세요.

## 2. 리뷰어 체크리스트

- [ ] **정확성**: 요구사항대로 동작하는가, 경계값과 오류 상황을 처리하는가
- [ ] **보안**: 비밀 정보가 노출되지 않는가, 입력을 검증하는가, 워크플로우 권한이 최소한인가
- [ ] **테스트**: 변경을 검증하는 테스트가 있는가
- [ ] **가독성**: 이름이 의도를 드러내는가, 불필요한 복잡함은 없는가
- [ ] **문서**: 사용법이 바뀌었다면 문서도 바뀌었는가
- [ ] **범위**: PR이 하나의 목적만 다루는가

## 3. 리뷰 절차

1. 작성자는 PR 템플릿을 채우고, 스스로 먼저 diff를 읽어 봅니다.
2. 리뷰어는 **1 영업일 이내**에 첫 응답을 남깁니다.
3. `[MUST]`가 하나라도 있으면 `Request changes`, 없으면 `Approve` 또는 `Comment`로 제출합니다.
   - GitHub은 자신의 PR에 `Approve`/`Request changes`를 제출할 수 없습니다. 작성자 본인의 셀프 리뷰는 `Comment`로 제출하고, `[MUST]`가 모두 해결된 뒤 머지합니다.
4. 작성자는 모든 `[MUST]`와 `[SHOULD]`에 수정 커밋 또는 답글로 대응합니다.
5. 모든 대화가 해결(Resolve)되면 Squash merge 합니다.

## 4. 좋은 리뷰를 위한 원칙

- 명령이 아니라 제안으로 씁니다. "이렇게 하세요" 대신 "이렇게 하면 어떨까요".
- 이유를 함께 적습니다. 이유 없는 지적은 배울 것이 없습니다.
- PR은 작게 유지합니다. 변경이 400줄을 넘으면 나누는 것을 고려합니다.
- 잘한 점도 적습니다.
