# ADR-0002: Feature 브랜치 전략과 Squash merge를 사용한다

- 상태: Accepted
- 날짜: 2026-11-15
- 결정자: @jang-ssi

## 배경

`main`에 직접 커밋하던 방식에서는 리뷰 없이 변경이 들어가고, 커밋 메시지 형식도 제각각이었다. 동시에 `main`에는 DORA·스프린트 리포트를 갱신하는 자동화 봇이 매일 커밋한다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|------|------|------|
| Git Flow (`develop`, `release` 브랜치) | 릴리스 주기가 긴 제품에 적합 | 1인·소규모 저장소에는 브랜치가 과함 |
| Trunk-based (main 직접 커밋) | 가장 단순 | 리뷰와 CI 관문이 없음 |
| GitHub Flow (Feature 브랜치 + PR) | 단순하면서 리뷰·CI 관문 확보 | 브랜치가 오래 살면 충돌 |

## 결정

GitHub Flow를 따른다. `main`에서 `type/설명` 형식의 브랜치를 만들고, PR 리뷰와 CI를 통과하면 **Squash merge** 한다. 커밋과 PR 제목은 Conventional Commits를 따른다.

## 결과

- 좋아지는 점: `main` 히스토리가 PR 단위의 한 줄로 정리되고, 제목만으로 변경 유형을 알 수 있다.
- 감수하는 점: 브랜치 안의 세부 커밋 이력은 PR 화면에서만 볼 수 있다.
- 후속 작업: 자동화 봇의 직접 푸시를 막지 않도록, 브랜치 보호 규칙은 강제 푸시·삭제 금지와 선형 히스토리 중심으로 설정한다.
